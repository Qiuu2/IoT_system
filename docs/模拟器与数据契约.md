# 设备模拟器与数据契约

> UI 原型：https://claude.ai/code/artifact/39e9dd81-6011-4e61-83c1-d0de713ce719

硬件到货前，用模拟设备解耦 L1–L3，让 L4–L9 全速开发。模拟器后期直接变成
自动化测试的桩，不是一次性投入。

## 快速开始

```bash
python3 sim/run.py --selftest       # 协议自检：每种设备真的能通
python3 sim/run.py                  # 起 156 台模拟设备 + 采集循环 + API
python3 sim/run.py --export d.json  # 采集若干轮后导出数据集
python3 sim/ui_payload.py d.json p.json && python3 sim/build_ui.py p.json ui/prototype.html
```

无第三方依赖，只用标准库。

## 分层与文件

| 文件 | 对应层 | 职责 |
|---|---|---|
| `sim/drivers/*.json` | L1 | 驱动定义：传输方式、指令集、探测方式、**可信度标注** |
| `sim/device.py` | — | 模拟设备运行时（假设备，将来删掉） |
| `sim/collector.py` | L1 | 采集器：真的说这些协议，输出归一化 `Reading` |
| `sim/topology.py` | L2 | 从 BOM 生成空间树与设备台账 |
| `sim/world.py` | L4/L5 | 预约、告警聚合、工单派生 |
| `sim/run.py` | — | 编排：起设备、跑采集、开 HTTP API |
| `ui/prototype.template.html` | L7 | 界面原型模板（数据由构建脚本注入） |

真设备到货时，**只有 `sim/collector.py` 里的 client 需要替换**，`Reading`
结构与其上的一切不动。`sim/device.py` 整个删除。

## 关键约束：区分「清单写明的」与「我们猜的」

清单给了传输层参数，**没给指令码表**。如果把猜的指令当成真的，
UI 和数据模型会围着错误假设长起来。所以每个驱动都带机器可读的可信度标注：

```json
"confidence": {"transport":"confirmed","framing":"guessed",
               "commands":"guessed","telemetry":"confirmed"}
```

| 驱动 | 型号 | transport | commands | 说明 |
|---|---|---|---|---|
| `rel08` | EMeta-REL08-1U | confirmed | **confirmed** | Modbus-TCP 是公开标准，模拟的报文和真机一致 |
| `pnc218` | EMeta-PNC218 | confirmed | guessed | 通道数/波特率/电压电流回传清单写明，指令语法是猜的 |
| `pnc809` | EC-PNC809 | confirmed | guessed | 同上 |
| `rs6608` | EMeta-RS6608 | confirmed | n/a | 透传通道，本身无指令集 |
| `ir8` | EMeta-IR-8RJ45 | confirmed | guessed | 清单未写状态查询指令，故只做建连探活 |
| `matrix88` | EMeta-JZ-M0808S | **guessed** | guessed | 清单未写控制方式，按 AV 矩阵行业惯例假设 |
| `chm9` | EM-PM-CHM9 | **guessed** | guessed | 同上 |
| `generic-tcp` | — | confirmed | n/a | 只判在线离线，对应截图的「检测方式 PING」 |

拿到厂商协议文档后，改 `commands` 段与 `confidence`，其余不动。
**任何标 `guessed` 的字段都不能作为需求评审或验收的依据。**

## 采集完全由驱动声明驱动

采集器不对任何型号做特判，探测方式来自驱动的 `probe` 段：

```json
"probe": {"mode":"line","query":"STAT?",
          "fields":["voltage","current","channel_bits"]}
```

`mode` 取 `line` / `modbus` / `tcp`。`fields` 决定每个 token 落到哪个指标，
驱动没声明的东西一律不产出。早期版本把解析写死在采集器里，导致红外扩展器
的 `STAT 0` 被当成「电压 0.0V」——这类 bug 靠声明式配置从结构上避免。

## 数据契约（HTTP API）

`python3 sim/run.py` 后可直接调用。UI 依赖的是这份契约，不是模拟器。

| 端点 | 返回 |
|---|---|
| `GET /api/overview` | 设备在线/离线、告警数、今日会议、空间数 |
| `GET /api/spaces` | 空间树（楼层 → 会议室，含面积） |
| `GET /api/devices` | 设备台账 + 最近一次实时读数 |
| `GET /api/readings` | 归一化读数快照 |
| `GET /api/alarms` | 聚合后的告警 |
| `GET /api/bookings?date=YYYY-MM-DD` | 预约 |

归一化读数结构（上层只认这个，不关心底下是 ASCII 还是 Modbus）：

```json
{"device_id":"DEV-0022","online":true,"latency_ms":22.2,
 "metrics":{"voltage":219.6,"current":16.6},
 "channels":[true,false,...],"extra":{},"raw":"STAT 219.6 16.60 101...","error":null}
```

## 故意造出来的「乱」

全在线的数据看不出 UI 问题。当前注入：

- **10 台离线**（约 8%，按设备 ID 稳定哈希选取，每次运行结果一致）
- **2 台过压 + 1 台欠压**，只注入到有电压遥测的时序电源上，否则观测不到
- **预约含跨天会议、背靠背会议、12% 已取消**
- 采集多轮，让告警的 `occurrences` 真实累积

## 建模过程中发现的两个问题

**1. 告警必须按 `(设备, 告警码)` 聚合。**
一台离线设备每轮询一次就产生一条告警，10 秒一轮的话一小时 360 条。
现在同一故障始终是一条记录，只累加 `occurrences` 和 `last_seen`，
故障恢复后自动置 `recovered`，而不是留一条永远待处理的僵尸告警。
当前 13 条在告故障，累计发生 6310 次——**如果不聚合，告警中心第一天就废了**。

**2. 端口与 IP 要分开建模。**
真实部署里每台设备有独立 IP，端口可以重复（都是 502、8801）；模拟器全挤在
127.0.0.1 上必须换端口。设备记录里的 `port` 始终是真机端口，模拟端口另开
21000+ 一段，两者不混淆——否则将来配置真设备时会踩坑。
